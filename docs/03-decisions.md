## 使用方法

- 每个需要拍板的问题对应一个 D 编号。编号不复用。
- 状态：**待定**（有建议，未决定）→ **已定**（写明结论、日期、依据）→ 必要时 **已推翻**（链接到新的条目）。
- 做出决定后，同步更新受影响的需求或技术方案，并在“影响”一列列出的位置去掉〔待定〕标记。
- 依据尽量是实测记录或用户反馈，不以框架宣传指标作为依据。

## 条目详情

### D-01 Windows 桌面容器

- **建议**：先验证 Electron + React + TypeScript；Electron 的透明穿透、全屏识别或资源占用无法满足时，评估最小 Windows 原生桥接，仍不行再考虑 WPF。
- **决定依据**：P0 桌面交互与系统上下文原型的实测记录。
- **约束**：在 P0 决定，不在功能完成后推倒重来。

### D-02 首个模型服务与协议

- **建议**：选择一个同时支持流式、工具调用、取消的服务，接入一个适配器，接口保持可替换。
- **选择条件**：
  1. 能力矩阵满足 TD §7.1（流式、工具调用、工具结果续传、取消、错误码）。
  2. **目标用户所在网络能稳定访问**（例如中国大陆用户访问部分海外服务不稳定）。
  3. 中文理解与时间表达提取在评估集上的表现。
  4. 成本与延迟。
- **决定依据**：P0 模型协议原型和评估集的小批测试。
- **M5 采用（2026-11-24，按产品负责人要求）**：首个适配器为 OpenAI 兼容协议（`/chat/completions` + SSE），预设 DeepSeek、通义千问、Kimi、智谱、本地 Ollama 和自定义地址；网络请求用 Electron `net.fetch`，跟随系统代理。其他协议以新的 `AdapterDefinition` 加入注册表。M5 不使用工具调用（`toolCalls: false`），工具调用在 M6 对所选服务实测后开启。
- **M6 实现（2026-11-27）**：OpenAI 兼容适配器开启工具调用（`tools` + `delta.tool_calls`）；服务或模型拒绝带工具的请求（HTTP 400）时降级为只聊天并记住。已用 mock 和本地 HTTP 服务验证协议，尚未在真实服务上验证工具调用、畸形参数和取消。
- **状态**：待定。真实服务实测记录见 [verification/M5.md](verification/M5.md)、[verification/M6.md](verification/M6.md)。

### D-03 应用退出后是否用系统级计划通知

- **背景**：应用退出后无法实时提醒，开机启动又默认关闭，用户重启电脑后忘开应用会错过提醒。
- **建议**：P0 验证 Windows 的计划通知（ScheduledToastNotification），确认在应用退出后能否按时弹出，以及应用身份（AUMID）、安装方式、改期/取消同步撤销的可行性。
- **若可行**：提醒创建时同时注册系统计划通知，改期、取消时同步撤销；已知限制 §3.3 第 1 条相应缩小。
- **若不可行**：维持“首次创建提醒时提示开启开机启动 + 成功卡片标注运行条件”的方案。
- **M4 现状（2026-11-24）**：尚未做 P0 验证，先按“不可行”分支实现；验证可行后再加入系统计划通知。

### D-04 外部全屏时宠物的默认行为

- **建议默认**：识别到外部全屏 → 宠物自动隐藏，退出全屏后恢复；识别结果未知 → 宠物保持显示，但不使用会盖过全屏窗口的置顶层级。用户可以改为“全屏时保持显示”。
- **待确认**：P0 实测各类全屏（游戏、视频播放器、浏览器全屏、演示软件）下的识别率，以及“不盖过全屏”的置顶层级是否可行。
- **M2 实现（按建议默认）**：Windows 上用 koffi 调用 user32/shell32，每秒读取一次前台窗口；前台窗口不是桌面/任务栏、未最大化、矩形覆盖整个显示器，或系统报告独占全屏/演示模式时，判定为全屏；只在与宠物同一显示器时隐藏宠物。宠物只使用普通置顶层级。
- **已有证据（2026-11-24，Windows 11 10.0.26200，单屏 2560×1440 100%）**：覆盖整屏的无边框窗口能识别并隐藏、退出后恢复；最大化和普通窗口不误判。浏览器视频、播放器、游戏、演示软件尚待手测，见 [verification/M2.md](verification/M2.md)。
- **状态**：待定，手测完成后关闭。

### D-05 SQLite 驱动

- **候选**：better-sqlite3（成熟，需要原生模块重建）；Electron 内置 Node 的 `node:sqlite`（免原生模块，但稳定性需要核实）。
- **决定依据**：P0 在所选 Electron 版本上验证安装、打包、事务、WAL、备份 API 和稳定性标记。
- **M3 采用 `node:sqlite`**：Electron 45.4.1 内置 Node 24.22.3、SQLite 3.54.1，加载时没有实验性警告；提供 `DatabaseSync`、事务和 `backup`，用 `VACUUM INTO` 做一致性备份。不需要原生模块重建。存储访问封装在 `storage/database.ts`，切换驱动只改这一处。
- **已有证据（2026-11-24，开发机）**：真实临时库上的单元测试（事务、迁移、回滚、备份）通过；开发版创建数据、重启后仍在。
- **状态**：待定。在无开发环境的机器上验证打包版读写和升级后关闭。

### D-06 对话流式方案与首字延迟目标

- **候选 A（两段式）**：先缓冲决定动作，再无工具流式表达。可靠，但普通聊天基线为两次请求。
- **候选 B（单次流式 + 撤回）**：一次请求流式显示；流中出现工具调用时，收起已显示的文字，转为“执行 → 解释”。延迟低，但依赖模型很少“先说话再调工具”。
- **建议**：P0 用同一评估集测两种方案的首字延迟、调用次数，以及 B 方案中需要撤回文字的比例，再决定；NFR-04 的首字延迟目标（P50 ≤ 2.5 s、P90 ≤ 5 s）同时定稿。
- **M5 现状**：没有工具调用，纯聊天直接单次流式；两种方案的比较在 M6 引入工具时进行。
- **M6 计划（2026-11-27）**：两种方案都实现为可切换的轮次策略，用 M6 评估集在真实服务上对比后选定默认方案并关闭本条，见 [04-roadmap.md](04-roadmap.md) M6。
- **M6 现状（2026-11-27）**：两种方案已实现（设置页“对话方式”，暂定默认两段式）；每轮记录请求次数、首字时间、撤回次数和撤回前是否有成功声明。真实服务对比待用户提供密钥后运行 `tests/eval/live.test.ts`，结果填入 [verification/M6.md](verification/M6.md)。

### D-07 专注时长的统计口径

- **建议**：统计时长以计划时长为上限；到期后经过的时间不计入；期间睡眠或锁屏的时长单独标注。
- **待确认**：用户是否需要“专注统计”页面；如果不需要，只保留单次结果展示。

### D-08 本机聊天记录的默认保留期

- **建议**：默认永久保留，设置中可选 30 天或 90 天，并支持手动删除。
- **考虑**：保留越久，记忆回溯越完整，但隐私暴露面越大。模型上下文只携带有限历史，与保留期无关。

### D-09 卸载时是否默认删除数据

- **建议**：默认保留，卸载程序提供“同时删除我的数据”复选框并显示数据位置。
- **考虑**：误删的代价大于残留的代价。

### D-10 最终角色与十二类动作

- **建议**：原创 2D 角色，先占位后替换；动作清单见 R04.AC-1。
- **决定时点**：P2 美术制作前，与美术协作定稿，并确认素材许可。

### D-11 含糊时间的默认范围

- **建议**：使用用户已配置的范围；没有配置时询问一次并保存。首次设置可提供预设（例如上午 9:00–12:00、工作日周一至周五），用户可编辑。
- **决定依据**：P1 中文表达测试。
- **M7 计划（2026-11-27）**：M7 不做安静时段等时间范围偏好，本条随 R13 主动陪伴一起决定，见 [04-roadmap.md](04-roadmap.md) M7“本里程碑不做”。

### D-12 安装包签名与分发

- **建议**：自用阶段只做安装验证；对外发布前再确定代码签名证书和分发渠道。

### D-13 安静模式下是否默认使用系统通知

- **M4 暂定**：默认不用系统通知（安静时只进信箱），托盘提供“安静时用系统通知提醒”开关。

- **建议**：默认不使用系统通知，提醒只进入信箱并在宠物上显示未读标记；在首次使用流程中让用户选择。
- **考虑**：安静模式下用户仍希望收到自己设的提醒，但不希望被闲聊打扰；系统通知只用于提醒和约定跟进，不用于普通陪伴。

### D-14 每日资讯首版支持哪些内容源类型

- **背景**：用户要求“先作为一个功能，后续可以扩展”。架构上内容源是可插拔的（TD §19.2），这里只决定首版内置哪几种。
- **候选**：
  | 类型 | 优点 | 风险 |
  | --- | --- | --- |
  | RSS/Atom 订阅 | 标准、稳定、来源可控，合规风险低 | 给的是“最新”而非“最热”；不少中文网站没有 RSS |
  | 热榜（微博热搜、知乎热榜等） | 最接近“热点” | 多无官方接口，网页改版即失效，有条款风险 |
  | 新闻/搜索 API | 结构化、可按主题检索 | 需另申请密钥、可能收费，国内可达性需确认 |
  | 模型服务自带的联网搜索 | 接入最简单 | 来源不可控、易编造，依赖所选服务（D-02） |
- **建议**：首版只内置 RSS/Atom，预置几个可编辑的中文源作为示例；其他类型作为后续扩展，按真实需求逐个接入。
- **状态**：待定。

### D-15 公众号文章抓取方式与订阅能力

- **单篇链接**：微信“复制链接”得到的 `mp.weixin.qq.com/s/...` 通常是可公开访问的网页，正文可抽取。P2 需实测：
  1. 不登录直接抓取的成功率；
  2. 触发“环境异常”验证的频率阈值；
  3. 已删除、违规、仅图片文章的识别；
  4. 标题、公众号名称、发布时间等字段的抽取规则稳定性。
- **自动订阅某公众号的更新**：微信没有面向订阅者的开放接口。可行路径都依赖第三方桥接（例如借助其他微信系产品账号自建 RSS 的服务），存在账号风险、条款风险和失效风险。
- **建议**：首版只支持用户提交的单篇链接和粘贴正文；“订阅公众号”作为未来的一种内容源，单独评估后再决定，不进入首版。
- **状态**：待定。

### D-16 内容摘要的模型与用量上限

- **建议**：摘要任务与对话共用 ModelAdapter，但允许单独配置一个更便宜的模型；设每日 token 上限（默认值在 P2 根据实测用量确定），超过后暂停自动摘要并在信箱提示，用户手动触发不受限或另设上限。
- **状态**：待定。

### D-17 文章正文的本地保留期

- **建议**：摘要、标题、链接、来源永久保留；抽取的正文默认保留 30 天（用于追问），可设为永久或不保留。导出时默认不包含正文。
- **考虑**：保留正文便于追问和重新总结；但占用空间，也涉及第三方内容版权。仅限本机个人使用，不提供分享或发布能力。
- **状态**：待定。
