# 桌面陪伴宠物：产品需求与验收基线

> 版本：v0.2 方案草案｜日期：2026-10-29  
> 来源：原始 [AGENT.md](AGENT.md)。本文拆出产品目标、范围和可观察行为，不绑定具体框架。  
> 状态：尚未实现、尚未验收。“要求”是目标，不代表已有能力。  
> 技术实现见 [TECHNICAL_DESIGN.md](TECHNICAL_DESIGN.md)。新增的默认值与取舍均属于本次建议，实施后按证据调整。

## 1. 产品定位

面向 Windows 桌面的个人陪伴宠物：能互动，能连续理解正在进行的事情，能把明确请求变成真实的本地操作，在合适时机跟进。

主要服务一个本机用户，首版中文，Windows 10/11 x64。不建设账号体系、云端同步或多人服务。

核心体验是：

```text
用户分享一件事 → 当下有合适回应 → 需要时记录或执行
             → 得到许可或明确约定后跟进 → 用户更新进展
             → 下次能接上；值得纪念时由用户决定保存
```

“能聊天”“能计时”“有宠物动画”分别完成，不等于核心体验完成。必须验收它们围绕同一件事情形成的完整流程。

## 2. 成功标准和边界

1. 用户能把宠物长期留在桌面，不被透明窗口挡住工作，不被频繁抢焦点或打断。
2. 明确操作有真实结果。失败、缺信息、正在等待都不显示为完成。
3. 重启后工具数据、有效偏好、当前事项和已安排的跟进仍存在。
4. 用户能查看、更正和删除保存的信息，旧结论不会因纠正而反复出现。
5. 主动互动有依据、可控制；忽略宠物不产生惩罚、负罪感或永久人格判断。
6. 没有配置模型或断网时，本地交互、表单工具、提醒和已有数据可用。
7. 使用云模型时，明确告知相关输入会发送到配置的模型服务。

首版不提供：语音、后台截屏、摄像头、全量键盘记录、任意电脑控制、外发消息、付款、联网内容发现、跨设备同步、插件市场、复杂养成。

应用真正退出后不保证实时提醒；下次启动可查看和处理错过的事项。关闭工具面板与真正退出必须有明确区别。

## 3. 用户场景

### U1：认识与相处

用户打开应用，看到宠物并能拖动、触碰、打开小窝。可以设置称呼、表达风格、主动程度、安静时段、角色尺寸和动态效果。未配置模型也能完成以上操作。

### U2：随手记录与真实行动

用户说“明天下午三点提醒我改简历”，获得具体本地日期时间的结果卡片；重启后安排仍在。说“下午提醒我”时，应用询问具体时刻，尚未安排前不声称成功。

用户也能直接用表单完成同样操作，模型不是工具的唯一入口。

### U3：延续一件事

用户说“最近在准备面试”，宠物可以接话，但不自动声称已经设置提醒。用户说“记住我在准备产品经理面试”后，形成可查看的近期事项。用户明确说“周五晚上八点问问我准备得怎么样”后，产生独立、可取消的跟进安排。

以后问“面试那件事还记得吗”，宠物使用已保存的信息和进展。没有结果时询问进展，不编造“已经通过面试”等结论。

### U4：安静陪伴与专注

用户开始 25 分钟专注，普通主动闲聊暂停。睡眠、锁屏或重启后计时状态符合约定；到期不自动把关联待办标成完成。

### U5：纠正与忘记

用户更改称呼，之后使用新称呼。用户纠正面试时间后，不再沿用旧时间。用户忘记一条记忆后，它不再通过检索、摘要或后台待处理候选自动进入模型上下文。

可单独删除相关历史对话；界面区分“不再用于记忆”和“删除本机记录”，说明备份及已发送至模型服务的数据不受本机删除直接控制。

### U6：形成共同回忆

完成一件事情后，用户可以接受保存回忆的提议或自行创建。回忆在相册中可查看、修改、删除，可关联预置原创摆件。任务完成不自动等于用户愿意长期保存。

## 4. 需求清单

编号用于技术设计和测试追踪，不表示独立微服务或开发包。

| ID | 需求 | 完整首版的验收要求 |
| --- | --- | --- |
| R01 | 桌面生命周期 | 单实例、托盘、显示/隐藏、打开小窝、真正退出；关闭面板后后台提醒仍工作 |
| R02 | 身体互动 | 透明桌宠、拖动、触碰、落地、边缘吸附、右键菜单；透明区不阻挡桌面点击 |
| R03 | 屏幕适配 | 多屏位置恢复；显示器移除后可找回；100%/125%/150% 与混合 DPI 验收 |
| R04 | 角色表现 | 一个原创 2D 角色，约十二类语义动作；错误不播放成功反馈；支持缩放与降低动态效果 |
| R05 | 对话 | 文本输入、流式输出、停止生成、有限历史；状态明确，失败可重试 |
| R06 | 随手记 | 创建、列表、搜索、修改、删除、短期撤销；中文基础搜索可用 |
| R07 | 待办 | 创建、查看、修改、完成、记录进展；完成状态由真实操作决定 |
| R08 | 一次性提醒 | 创建、查看、改期、取消、到期展示、推迟；重启/睡眠恢复；旧版本不再次提示 |
| R09 | 专注 | 开始、暂停、继续、取消、结束；同一时刻最多一个活动会话；可关联待办 |
| R10 | 显式偏好 | 称呼、表达方式、兴趣、主动程度、安静时段，可直接设置、编辑和清除 |
| R11 | 近期事项与记忆 | 已确认信息有来源；事项能保存进展；过期、纠正、忘记后不再使用旧结论 |
| R12 | 约定跟进 | 保存对象、目的和时间；可查看、改期、取消；任务结束后无效跟进可停止 |
| R13 | 低频主动陪伴 | 有依据、配额、冷却、反馈；安静/专注/锁屏/全屏抑制；无回应自然结束 |
| R14 | 兴趣内容 | 仅使用用户提供、收藏或应用原创内容；不伪装实时搜索 |
| R15 | 小窝 | 小本子、沙漏、信箱、相册、小箱子、相处设置；与桌宠卡片共享同一份业务数据 |
| R16 | 共同回忆 | 用户创建或确认后保存；可修改、删除、关联摆件；换皮肤保留个人数据 |
| R17 | 文字拖入 | 类型和长度检查，选择记笔记或加入对话；文件拖入明确告知当前不支持 |
| R18 | 模型设置与离线 | 设置服务地址、模型和密钥；连接失败不破坏本地功能；不在界面或导出泄露密钥 |
| R19 | 数据管理 | 数据持久化、可迁移；导出、恢复与清理；恢复失败不破坏现有数据 |
| R20 | 发布质量 | 可安装版和解压版；目标 Windows 实机验收；来源许可清楚；一周核心场景验收 |

“安静”不等于永久丢弃用户安排的提醒。提醒仍进入信箱；是否额外使用系统通知由独立设置控制。

## 5. 分阶段交付范围

以下是开发与验收顺序，不是取消完整首版需求。

### P0：技术可行性验证

使用占位角色，验证透明点击、拖动捕获、焦点、多屏、外部全屏识别、数据库打包和模型能力。产出可运行试验程序和实测记录，不宣传为完整产品。

### P1：可自用 MVP

交付桌宠基础交互、简单小窝、真实本地工具、一个模型适配器、显式偏好、近期事项、明确约定的跟进、基础记忆管理、数据导出恢复及安装包。

优先验证 U2、U3、U4、U5。P1 可使用占位素材；尚未完成的完整首版功能必须列在发布说明中。

### P2：完整首版

补齐原创角色动作、低频主动互动、兴趣卡片、待确认记忆候选、共同回忆和摆件、完整小窝体验、文字拖入以及剩余屏幕/性能/可访问性验证。

通过 R01～R20 和一周核心场景，才能称为本文定义的完整首版。

## 6. 建议默认值

这些值原方案部分已提出，部分在本次明确；均须在体验测试后调整。

| 项目 | 初始建议 | 用户可见含义 |
| --- | --- | --- |
| 非必要主动互动 | 默认标准档，每日本地日期最多 2 次，间隔至少 60 分钟；支持关闭 | 宠物不会持续主动打断 |
| 提醒与约定跟进 | 不计入普通闲聊配额；相近到期项合并展示 | 用户的明确约定不被闲聊额度阻断 |
| 安静时段 | 首次设置提供可编辑预设，不凭一句模糊表述偷偷推定全天规则 | 生效范围可查看 |
| 专注计时 | 自然经过时间计时，睡眠/锁屏仍计时 | 回来时不会无故多出一段专注时间 |
| 过期提醒 | 24 小时内给一次汇总，更早仅入信箱 | 重新打开不会连续弹出大量旧提醒 |
| 离线聊天输入 | 保留为待重试，联网后不擅自发送 | 用户知道哪些内容已发给服务 |
| 模型提取偏好 | 先待确认，不能覆盖显式偏好 | 猜测不会变成长期事实 |
| 开机启动 | 用户选择，默认不开启 | 提醒依赖后台运行的条件明确 |

## 7. 可验证的质量要求

- 数据：强制关闭后，已显示成功的本地写入能恢复；参数不合法和迁移失败不破坏旧数据。
- 幂等：同一逻辑操作重试不重复创建；用户明确发起的第二次相同操作不能被错误吞掉。
- 交互：不抢输入焦点；宠物窗口不覆盖整屏截获输入；拖动与摸头可区分。
- 提醒：测试正常到期、取消竞争、改期、重启、睡眠恢复、多个事项同时到期。
- 记忆：用固定多轮对话验证保存、更新、纠正、忘记、过期和来源删除。
- 主动性：没有有效依据不生成闲聊；配额跨重启保留；全屏识别未知时遵循保守策略。
- 性能：原方案的空闲 CPU 约 2%、内存约 300 MB 保留为测量目标，非已实现保证。报告记录硬件、窗口数量、素材、采样方法。
- 数据恢复：包含工具数据、偏好、有效记忆及调度状态；恢复后不会把旧提醒全部重新弹出。

## 8. 尚需用实测或产品反馈确定的事项

| 事项 | 当前建议 | 何时作最终决定 |
| --- | --- | --- |
| Windows 容器 | 先验证 Electron；必要时改用 Windows 原生外壳 | P0，不在功能完成后推倒重来 |
| 模型服务 | 先接一个具备所需能力的服务，提供可替换接口 | P0 能力测试后 |
| 最终角色与十二类动作 | 原创 2D，先占位后替换 | P2 美术制作前 |
| “上午”“工作时间”等含糊时间 | 使用用户已配置范围，否则询问；结果显示具体范围 | P1 中文表达测试 |
| 开机启动、安静模式下系统通知 | 独立设置并清楚说明 | P1 首次使用流程 |
| 安装包签名与分发 | 自用先完成安装验证；公开发布再确定签名和渠道 | 对外发布前 |

## 9. 文档定位

原 `AGENT.md` 可以作为需求来源和早期设计基线，但不是纯需求文档：它同时包含框架、数据库表、进程架构、测试和开发约定。

后续维护分工：

- 本文负责“用户需要什么、什么算做完”。
- `TECHNICAL_DESIGN.md` 负责“如何实现、为什么这样实现、怎样验证风险”。
- 原 `AGENT.md` 保留历史设计供对照；其技术细节不应阻止有证据的调整。
- 将来如需自动加载的 `AGENTS.md`，只放开发命令、代码边界、测试要求和上述文档入口，避免复制整套需求造成多份版本漂移。

用户后续明确要求优先于这些文档。实施时发生范围或验收变化，应更新本文；只调整技术实现而不改变用户行为时，更新技术方案即可。
